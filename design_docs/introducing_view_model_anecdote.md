# 引入 view model 的轶事

一开始，事情很简单。

这个小应用只要看 DeepSeek 余额。一个 provider，一张卡，一个刷新按钮，一个设置入口。代码直接写在页面里，也没什么问题。数据来了就显示，没来就空着。像一团刚揉好的面，粗糙归粗糙，至少知道自己要成什么形状。

后来 ChatGPT/Codex 进来了。

它带来的麻烦不是“多一张卡”这么轻巧。它不能自动登录，不能搞 stealth，只能走用户已经打开的 Safari 页面；读到页面文本还要解析，解析失败要能导出 diagnostics；用户有时想手动填，有时想从 Safari 读；更要命的是，哪怕已经有一份数据，也不能把“重新读取”和“手动修改”的入口弄丢。

于是开始加水。

这里补一个按钮，那里加一个状态。这个分支处理空数据，那个分支处理已有数据。DeepSeek 用一套订阅，ChatGPT 先临时写一套监听。每次修改都很小，看着也都合理。可改着改着，水多了，面稀了。

保存后能显示，重启后不一定能加载回来。空状态下入口齐全，有数据后入口又少了一个。一个分支刚修好，另一个路径又出了问题。问题不大，却很烦，因为它不是单个 bug，而是一堆交互承诺散在代码各处：哪些入口必须一直存在，哪些状态互不干扰，失败后要给用户什么退路。

这时再继续掺面，效果有限。

真正需要先揉清楚的是：dashboard 到底有哪些交互语义？顶部固定有哪些动作？DeepSeek 这张卡只管余额。ChatGPT 这张卡无论有没有数据，都应该保留 Safari 读取和手动输入。Safari 失败后要能回到手动路径。手动保存后要回到 dashboard。provider 的数据订阅也要按身份过滤，不能互相覆盖。

这些东西后来被写进了 interaction contract，也被收进了一个小的 view model。页面不再到处猜“现在该不该显示这个按钮”，而是先拿到一份整理好的菜单：header actions、balance provider、limit provider、每张卡有哪些动作。React 组件照菜单渲染，测试直接检查菜单。

这个变化不大，但很管用。

它没有把小应用改成大工程，也没有马上引入 router、store、state machine 或组件库。它只是承认：混乱已经存在了，只是之前藏在 JSX 分支和 hook 差异里。把它整理成交互契约和可测试的映射函数之后，后续修改就有了落点。

要加入口，看 contract。要改 dashboard，看 view model。要确认 ChatGPT 有数据后按钮还在，跑测试。要交给另一个 agent 继续做，也不用重新解释一遍“这个按钮为什么不能消失”。

返工代价也在这里变小。

没有这层归纳，每次改 UI 都像在湿面团里找形状：补一点，塌一点，再补一点。单次工作量不大，累积起来很耗神。有了契约之后，工作量前移了一点，但后面的反复确认少了，局部修补也不容易伤到别的路径。

这件事也说明，agent 协作不能只靠“谁来写代码”。有的 agent 适合快写，有的适合审边界，有的适合补测试，有的适合排障。它们要协作顺畅，中间需要一些可共享的东西：设计决策、交互契约、可测试的语义归纳、能带回来复现问题的 diagnostics。

代码是面，需求是水。面多了掺水，水多了掺面，偶尔能救急。可到了某个时刻，真正省事的办法是停一下，把它揉成形。
